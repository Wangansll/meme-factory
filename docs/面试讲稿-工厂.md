## 一、三档自述

### 30 秒版

> 一个用纯原生 JS 写的表情包生成器：输入一个"梗"，AI 出一整套九张表情包，可以选画风、透明抠图、九宫格下载。
> 没有框架也没有构建工具，前端 1900 行原生 JS，后端是 Node 原生 `http`，已经上线。

### 2 分钟版

> 这个项目的目的是把"AI 生成"做成一个普通人能用的工具：输入一个梗，选画风，点生成，出一整套九张风格统一的表情包。
>
> 技术上我做了两个刻意的选择：**不上框架**，所有交互用原生 DOM 写；**不上构建工具**，单个 `app.js` 直接跑。目的是把"框架帮我做的事"自己写一遍——状态怎么管、列表怎么增量更新、异步任务怎么取消。
>
> 里面比较有意思的是**异步任务**：生图一次要几十秒，提交后后端返回 `jobId`，前端轮询状态接口；用户中途取消用 `AbortSignal` 真正中断请求，避免"取消了还在后台渲染、回来又把旧结果贴上去"。
>
> 另外导出这块全是 Canvas：九宫格拼图、透明底预览、打包下载，都是画到 canvas 再 `toBlob` 生成文件，没引任何图像库。

### 5 分钟版

加第三节的四个机制细节 + 「取消那次竞态」的具体经过（见第五节 bug 1）。

## 二、一次生成的完整链路

```
① 用户输入梗 + 选画风 → POST /api/image  { prompt, style, ... }
   → 后端拼提示词（模板 + 风格后缀 + 文案）→ 调第三方生图
   → 立刻返回 { jobId }            ← 关键：不阻塞

② 前端 setInterval 轮询 GET /api/image/status?jobId=...
   → { status: 'pending' | 'done' | 'error', images: [...] }
   → done 拿到 9 张图的 URL

③ 渲染：结果按需插入 DOM（不整体重绘）

④ 导出：
   - 单张下载：直接 <a download>
   - 九宫格：9 张画到一张 canvas → toBlob → 下载
   - 透明底：canvas 去底后导出

⑤ 分享：POST /api/share { images } → 返回 sharecode
       别人打开 /?sharecode=xxx → GET /api/share/:code → 直接看到那一整套
```

## 三、四个核心机制

### 机制 1：异步任务 + 轮询（为什么不是长连接）

**问题**：生图要几十秒，HTTP 请求不能一直挂着。

**做法**：
- 提交接口只做"登记 + 触发"，立即返回 `jobId`；
- 前端轮询 `GET /api/image/status`，每次拿增量状态；
- 任务状态存在服务端内存/文件里，前端刷新页面也能继续轮询。

**追问：为什么不用 WebSocket / SSE？**
这个场景是**一次任务一次结果**，轮询 1~2 秒一次完全够，而且断线自动重连（下次轮询就是重连）。
上 SSE 要处理连接管理、代理超时、重连语义，收益是省几次请求——**不值得**。真要上，我会在"多任务同时进行、状态变化频繁"的场景才考虑。

**追问：轮询频率怎么定？**
按任务典型耗时定：几十秒的任务，1~2 秒一次；同时前端在页面不可见时降频或暂停。

---

### 机制 2：`AbortSignal` 真取消（不是"忽略结果"）

**问题**：用户点了取消，如果只是把 `isLoading` 置 false，请求还在飞，回来的时候又把结果渲染上去——用户看到"我明明取消了，图又出来了"。

**做法**：

```js
const ctrl = new AbortController();
try {
  const res = await fetch(url, { signal: ctrl.signal });
  ...
} catch (e) {
  if (e.name === 'AbortError') return;   // 静默退出，不报错
}
// 取消时
ctrl.abort();
```

配合一个"请求序号/任务 id"校验：结果回来时如果已经不是当前任务，直接丢弃。

**追问：取消要不要通知后端？**
要，但**不依赖它**。后端收到取消可以省算力；即使没收到，前端也不会再把结果贴上去——**正确性靠前端自己保证，不靠后端配合**。

---

### 机制 3：Canvas 合成与导出

**问题**：要"九宫格拼图"和"透明底"，但不想引图像库。

**做法**：
- 九宫格：`canvas` 3×3 布局，`drawImage` 逐张画，留白与圆角自己算；
- 透明底：把图片画到 canvas，用 `getImageData/putImageData` 处理边缘；
- 导出统一 `canvas.toBlob(cb, 'image/png')` → `URL.createObjectURL` → `<a download>` 触发下载。

**追问：为什么不用 html2canvas？**
html2canvas 是把 DOM 转图，体积大、样式支持不全、字体还容易错位。我这里**本来就有原始图片**，直接画 canvas 更准、更快、更小。

**追问：跨域图片 canvas 会不会被污染（tainted canvas）？**
会。`drawImage` 画了跨域图且没带 CORS 头，`toBlob` 会抛安全错误。所以生图结果要能带 `crossOrigin="anonymous"` 加载，或者由后端代理成同源。

---

### 机制 4：无框架下的状态管理

**问题**：没有 Vue/React 的响应式，状态变了怎么更新界面？

**做法**：状态集中在一个对象里，改完调一次 `render()`；渲染是**局部更新**——列表用增量 append，不重建整个 DOM（否则图片会重新加载、滚动位置丢失）。

**追问：那和框架比，你失去了什么？**
失去的是"数据变了自动 diff"。我要自己记得"改完状态调渲染"，且容易漏。收益是**小体积、零构建、启动快**，而且把 diff 这件事亲手写了一遍，反过来更能理解框架在做什么。

## 五、踩过的坑

### bug 1：取消后旧结果又贴上来（竞态）

先写了 `abort()`，但没做"结果是否属于当前任务"的校验：第一次请求被取消后，第二次请求发出，此时第一次的响应如果晚到（abort 生效前已到达），会把结果画上去。
**修法**：给每次请求一个递增 id，响应回来比对 id，不是当前任务就丢弃。
**这条最能体现"异步不是发出去就完了"**。

### bug 2：轮询把服务打满

一开始轮询间隔 300ms，多开几个标签页就把状态接口打出一堆请求。
**修法**：间隔放宽到 1~2 秒 + 页面不可见时暂停。

### bug 3：密钥不该进代码

生成接口一开始把第三方 key 写在 `server.js` 里。改成读 `process.env.PROVIDER_API_KEY`，没配时接口明确返回 `missing_provider_key` 而不是报 500 或假装成功。
**仓库里没有任何真实密钥**（`*.key`、`.env` 都在 `.gitignore` 里）。

## 六、主动承认的边界

1. **没有用户系统**：分享码即访问权，谁拿到链接谁能看，没有权限粒度。
2. **任务状态存本地文件**（`share-store.json`）：多实例会不一致，应该换数据库或 Redis。
3. **没有队列**：并发高了直接打第三方接口，会撞限流；应该有排队 + 重试。
4. **生成质量依赖提示词工程**：风格一致性靠拼接后缀，没有做参考图/微调。
5. **1.7 GB 生成素材没进仓库**：本地演示用的帧素材太大，只留了代码。

## 七、和场馆项目怎么对比着讲（面试常问"这两个项目区别"）

| 维度 | 场馆 | 工厂 |
|---|---|---|
| 规模 | 前后台 30+ 页面，有数据库 | 单页，状态在内存/文件 |
| 难点 | **并发正确性**（库存、金额、幂等） | **异步交互**（任务、取消、导出） |
| 取舍 | 用框架 + 类型系统换可维护性 | 不用框架换体积与"亲手写一遍" |
| 共同点 | 都不信前端、都把"失败"当正常路径处理 | 同左 |

**一句话总结**：
> 场馆练的是"数据不能错"，工厂练的是"交互不能乱"。
